SYSTEM ARCHITECTURE — CHATBOT PROCESSING PIPELINE
⌨️
1. User Input
User types a question or taps a quick-question chip. Raw text is captured from the input field.
🔤
2. Normalise
Input is converted to lowercase and trimmed. This ensures keyword matching is case-insensitive.
🔍
3. Intent Scan
Each of the 12 intents is scored by counting how many of its keywords appear in the normalised input.
🏆
4. Best Match
The intent with the highest keyword hit count (score ≥ 1) is selected as the matched intent.
↓ IF SCORE ≥ 1: RETURN INTENT RESPONSE  |  IF SCORE = 0: TRIGGER FALLBACK ENGINE
✅
5a. Response
The matched intent's response function is called, returning pre-written HTML content for the topic.
🔀
5b. Fallback
No match found. 3 random suggestions are drawn from the suggestion pool and displayed as chips.
💬
6. Render
The response HTML is injected into a bot message bubble with an animated entry transition.
📝
7. Log
The full processing trace — input, token scan, scores, result — is recorded to the Backend Inspector log.

⚠️ Risks & Limitations — Balanced View

  • This prototype uses simulated data only. No real Fortescue systems are connected.
  • Real implementation requires high-quality, continuous, calibrated sensor data across all target assets.
  • AI predictions are probabilistic. False positives and missed faults are both possible.
  • Human maintenance engineers must validate all recommendations before any intervention is ordered.
  • Data security, OT/IT integration, and governance require careful regulatory management.
  • Change management: field technician and planner adoption is critical to realising system value.
